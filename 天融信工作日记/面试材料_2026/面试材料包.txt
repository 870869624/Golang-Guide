3.1 NGDLP：敏感文件安全处理

一句话：解决"多个终端 Agent 并发上传敏感文件时，如何保证不损坏、不泄漏、可追溯"。

背景
终端 Agent 采集到敏感文件后上报管理中心，管理中心负责接收、校验、加密落盘，并支撑后续的检索、提取和下载。文件量大、并发高，且安全产品对"文件不能损坏、不能明文落盘"有硬要求。

挑战
· 同一文件可能被多个 Agent / 多个协程同时写入，存在竞态。
· 文件传输中途断连，不能留下半截脏文件。
· 文件落盘必须加密，下载要能解密，且要兼容历史密钥版本。

方案
1. 传输：gRPC 客户端流式上传（stream.Recv() 循环收到 EOF），分片携带 chunkHash，整文件校验 fileHash + MD5。
2. 并发控制：sync.Map 管理文件级细粒度锁，key 是文件路径，LoadOrStore 原子获取或创建锁；不是全局 mutex，不同文件之间不互相阻塞。
3. 原子写入：先写临时文件，完成后 os.Rename 原子替换；任何一步失败 defer 清理临时文件。
4. 加密：AES-256-GCM 分块加密，Nonce 写文件头，每块用块索引作 AAD；下载时动态解密并兼容多版本密钥回退。
5. 写入性能：FileBatchWriter 缓冲通道 + 批量 50 条 + 10 秒强制 flush，SensitiveFileUpdateQueue 单 worker 串行消费，避免 MongoDB 被突发写打爆。

效果
· 文件写入零损坏（【待补：日均文件量 / GB 数】）。
· 锁竞争延迟控制在毫秒级（【待补：实测数据；没测过就不要说这个数】）。

复盘（加分项，一定要准备）
"如果重来一次，我会把文件级锁换成基于 Redis 的分布式锁，或者把上传设计成无状态的分片对象存储，这样多实例部署时不会受单机锁限制；另外分片落盘和元数据写入之间还缺一个最终一致性的对账机制。"

高概率追问
· sync.Map vs map + RWMutex？→ 见 §5.1
· gRPC 客户端断连怎么感知？→ Recv() 返回错误，defer 清理临时文件
· 为什么不用 HTTP 上传？→ 架构统一用 gRPC、Protobuf 高效、强类型；代价是调试麻烦

3.2 NGEDR：威胁响应与威胁情报

一句话：把终端威胁"查得出来、看得懂、处置得掉"——多维查询 + RBAC 数据隔离 + 批量任务下发 Agent。

背景
EDR 产品每天产生大量病毒/恶意行为/高级威胁事件，安全运营人员需要按终端、按威胁、按溯源三种视角查询，并批量执行信任、清除、恢复隔离区、样本提取等操作。

挑战
· 多源数据 + 三种查询维度，数据模型与索引设计复杂。
· 不同角色只能看自己管辖分组内的终端数据，越权是安全产品的高压线。
· 一次批量处置可能涉及成百上千台终端，任务要按 Agent 聚合后下发。

方案
1. 三种查询维度：agent / threat / trace；按 MD5 的溯源查询走专用索引、不分页；log_type 映射为中文事件类型。
2. RBAC 数据过滤：调 RolesvcRPC 递归获取角色管辖的分组 ID，非空时向 MongoDB 注入 group_id: {$in: [...]}，为空代表全量权限。
3. 元信息填充：查询结果里的 agentID 批量调用资产服务 SearchAgent，补齐在线状态、OS、负责人，避免自己存一份容易不一致的冗余数据。
4. 批量处置：actionType 映射任务类型；SameHash=true 时按 MD5 反查全部关联记录，再按 AgentID 分组，每台 Agent 发一个批量任务；统一走 TaskSendNotCreateTask。
5. 情报模块：Excel 批量导入用"规则+类型 / 文件路径"做去重 key，先加载存量到 map 防重复；导入后异步下发策略同步，不阻塞接口返回；导出每 10 万行分一个 Sheet。
6. 安全细节：regexp.QuoteMeta 防正则注入，分页参数做负数/零值防御，错误提示走 i18n。

效果
· 权限越界事件为零（【待补：终端规模 / 日均威胁量】）。
· 情报导入从人工逐条录入改为 Excel 批量，且可重复导入不产生脏数据。

复盘
"当前的 RBAC 权限是每次查询实时计算的，量大了会有开销，可以用 LRU 做短时缓存（项目里其实已有 5 分钟 LRU 的先例）；另外任务下发目前是'发出去就不管'，要做得更稳需要补执行回执和失败重试。"

高概率追问
· RBAC 数据过滤在大数量下怎么优化？→ 见 §5.5
· 任务下发失败怎么办？→ 见 §5.6
· 三种维度的索引怎么设计？→ tenant_id + 时间/分组/病毒名/IP/MD5 复合索引

3.3 UEFUN：支付全链路 + 数字藏品（城汇玩）

一句话：一人独立负责后端从 0 到 1，把"钱"和"链上资产"两条容易出错的链路都跑通了。

背景
综合活动社区平台，涉及活动报名、部落社区、订单支付、数字藏品、提现结算。团队小，后端全部由你独立负责。

挑战
· 支付回调会重试，退款与分账有互斥关系，任何一处幂等没做好就是资金差错。
· NFT 铸造横跨链上交易和链下存储，任何环节都可能失败，但用户已经付过钱。
· 活动报名涉及限量票型，并发下不能超卖。

方案
1. 支付闭环：微信支付 V3 JSAPI，直连商户 + 服务商双模式；订单状态机 待支付 → 支付中 → 已支付 → 已分账/已退款 → 已关闭；唯一索引 + 状态机校验做幂等；回调用平台公钥验签。
2. 退款/分账互斥：退款前查分账状态，已分账先回退分账再退款；分账走 RabbitMQ 异步，完结分账用定时任务兜底。
3. 兜底查单：定时任务扫描超时未支付/支付中订单，主动调微信查单接口确认状态。
4. NFT 流水线：支付成功 → 建铸造记录 → RabbitMQ 异步合约调用 → 轮询交易回执 → 上传 IPFS 拿 CID → 更新元数据；每步可独立重试。
5. 库存：MySQL SELECT FOR UPDATE 行锁 + 版本号乐观锁；超时未支付订单由 cron 释放库存。
6. 工程化：Gin + GORM + MySQL + Redis + RabbitMQ 三层架构；golang-migrate 管理 65 个迁移版本；robfig/cron 13 个定时任务；Swagger 全量接口；Prometheus 指标。

效果
· 上线至今无资金差错（【待补：支付量级 / 商户数】）。
· 活动报名零超卖，积分结算准确率 100%。

复盘
"现在回头看，定时任务在单实例上是够用的，但多实例部署会重复执行，应该换成带分布式锁的调度器；分账和退款的强一致性如果重做，我会引入独立的资金流水表做对账，而不是只依赖订单状态。"

高概率追问
· 回调一直不来怎么办？→ 定时查单兜底，见 §5.2
· 分账和退款怎么互斥？→ 见 §5.3
· 区块链交易 pending 太久？→ 见 §5.10
· Redis 挂了库存怎么办？→ 当时库存扣减没有依赖 Redis，见 §5.7

4. 线上/现场故障案例库（讲"你处理过什么线上问题"用这一节）

这五个案例都来自你的工作日记，有真实命令和根因，比抽象地说"我排查过线上问题"强十倍。
讲述统一用：现象 → 定位 → 处置 → 根因 → 沉淀。

4.1 K8s Pod 大面积 Evicted

· 现象：客户现场大量 Pod 处于 Evicted / Pending / Error。
· 定位：kubectl top nodes、describe node | grep Conditions 看 MemoryPressure / DiskPressure / PIDPressure；describe pod 看 Events（"node was low on resource: memory"）；get pvc 看是否有 unbound PVC。
· 处置：清理 Failed/Evicted Pod → 临时把问题 Deployment 副本降为 0 → docker system prune -a -f --volumes 清理无用镜像和卷 → 恢复副本。
· 根因：节点磁盘/内存压力导致 kubelet 驱逐，现场环境镜像和日志堆积。
· 沉淀：把排查命令固化成 SOP；后续部署加磁盘/内存监控告警和日志清理策略。

4.2 ClickHouse Too many parts (300)

· 现象：Too many parts (300). Merges are processing significantly slower than inserts，查询失败。
· 定位：system.parts 查活跃 Part 数；确认写入模式是不是小批量高频 INSERT。
· 处置：先降低写入频率让后台 Merge 追上 → 低峰期 OPTIMIZE TABLE ... FINAL → 必要时临时放宽阈值（治标不治本）。
· 坑：OPTIMIZE 报 CANNOT_STATVFS 是数据目录/临时目录的 PVC 没挂对，kubectl exec ... df -h 确认挂载。
· 根因：小批量高频写 → Part 生成速度 > Merge 速度；也可能 CPU/磁盘 IO 打满、background_pool_size 太小。
· 沉淀：改批量写入策略（对应代码里的 FileBatchWriter：批量 50 + 10 秒 flush），把写入频率作为监控项。

4.3 MongoDB 索引缺失导致敏感文件提取超时

· 现象：现场触发外发后，敏感文件提取超时。
· 定位：进 Mongo 查 db.file.getIndexes()，用 explain('executionStats') 看查询是否走索引。
· 处置：补复合索引 {tenant_id:1, file_id:1, platform:1}；再用 explain 验证命中。
· 另一个相关问题：extract_progress 集合数据堆积导致 SFC 异常 → 清理 30 天前记录。
· 根因：现场数据量上来了，早期索引设计没覆盖实际查询条件；历史任务记录没有清理策略。
· 沉淀：把索引检查和 explain 验证纳入版本升级 checklist；给进度表加定期清理。

4.4 版本升级与 ClickHouse 数据迁移（26 → 30）

· 背景：南网现场版本升级，跨大版本且涉及 ClickHouse 表结构变化。
· 步骤：停全部服务 → 压缩备份 ClickHouse 数据目录 → 清理历史 mutation_*.txt → 只启动 ClickHouse → 跑 rebuild_ch.sh 迁移（中途不能中断）→ 无 WARNING/ERROR 后 --rename → 拉起全服务。
· 前置坑：0.28 之前升 30 会失败，需先删 /home/topsec/cache/ 下的 chart 目录。
· 经验：涉及数据目录的操作必须先完全停服 + 完整备份；单节点升级集群要先确认 PV/NFS 存储方式。

4.5 现场数据资产问题：临时文件提不上来

· 现象：触发外发后没有上报数据资产，管理中心下发提取任务也提不上来。
· 根因：客户端拷贝操作会生成临时文件（复制的内容可能不是文件而是文本），这类临时文件生命周期极短，管理中心异步下发提取时文件已经不在了。
· 面试价值：这是一个"技术之外还要理解客户端行为"的好例子，用来说明你不是只写接口，而是能定位端到端链路问题。

5. 高频追问题库（按优先级）

5.1【P0】sync.Map 文件锁为什么不用普通 map + Mutex？

答：
我当时比较了三种方案：
1. 全局 mutex：最简单，但粒度太粗，不同文件本来可以并发上传，会被串行化；
2. map[string]*Mutex + 全局 RWMutex：可行，但要自己保护 map 的并发安全，锁的创建和销毁都要额外处理；
3. sync.Map：本身并发安全，LoadOrStore 是原子操作，"不存在就创建锁、存在就复用锁"一步完成。

我们的场景是文件路径动态变化、读多写少，所以选了 sync.Map。它解决的是"锁本身的管理"问题，不是让加锁更快。

诚实边界：被问到底层 read map / dirty map 实现，就说"知道它内部做了读写分离来优化读多写少场景，具体晋升机制没有深入看过源码"。

5.2【P0】微信回调幂等 + 回调不来怎么办？

答：
两道保险 + 一个兜底：
· 唯一索引：以 out_trade_no 为唯一键，重复回调触发唯一键冲突，直接返回成功让微信停止重试；
· 状态机校验：只有"支付中"才能转"已支付"，已是终态就忽略；
· 兜底：定时任务扫超时"支付中"订单，主动调微信查单接口。

另外回调要先验签（平台公钥），防止伪造回调。

追问"如果回调处理时服务挂了？"：事务 + 唯一索引 + 状态机保证放学前重放也不会重复入账；查单任务会补上状态。

5.3【P0】分账和退款互斥怎么实现？

答：
退款前先查分账记录状态：未分账 → 直接退；已分账 → 先调分账回退接口，成功后再退款。订单状态机里把"已分账"到"已退款"设计为需要经过"分账回退中"的中间态，避免并发时两个操作交叉。

资金类的操作我都加了流水记录，方便对账。

诚实边界：如果被问分布式事务 TCC/Saga，答"项目规模没到那个程度，用的是本地事务 + 状态机 + 定时兜底；如果现在设计，我会加独立资金流水表做对账"。

5.4【P0】gRPC 流式传输的细节

答：
上传用的是客户端流（Client Streaming）：Agent 分批发分片，服务端 stream.Recv() 循环到 EOF；下载用的是服务端流。选 gRPC 是因为整体微服务通信统一用它，Protobuf 序列化和强类型有优势；代价是浏览器不原生支持、调试需要 grpcurl 之类的工具。

中途断连：Recv() 返回错误，defer 清理临时文件，不会留脏数据。分片和整文件都有 hash 校验，能发现传输不完整。

5.5【P1】RBAC 数据权限在大数据量下怎么优化？

答：
当前做法是先递归查角色管辖的分组 ID，再注入 group_id $in。量小的时候够用。

优化方向有三个：① 分组 ID 结果用短 TTL 缓存（项目里已有 LRU 5 分钟的先例）；② 在 tenant_id + group_id + 时间 上建复合索引，让过滤条件下推到索引；③ 如果分组特别多，改用预计算的权限位或宽表，避免超长 $in。

5.6【P1】Agent 任务下发失败怎么处理？

诚实答：
目前的实现是下发即返回，状态由业务侧记录，缺少执行回执和自动重试，这是我知道的短板。

如果要补，思路是：任务表记录状态（待下发/已下发/执行中/成功/失败）→ 失败进重试队列（指数退避，限制最大次数）→ 超过次数告警人工介入 → 终端侧上报执行回执做闭环。

5.7【P1】MySQL 行锁 / 乐观锁 / Redis 库存

答：
SELECT FOR UPDATE 是 InnoDB 行锁，命中索引才锁行，没命中索引会锁表，这是最容易踩的坑。乐观锁是加 version 字段，UPDATE ... WHERE version=?，影响行数为 0 说明冲突，重试或返回失败。

活动库存当时没有用 Redis 做扣减，因为 Redis 挂了保护就没了，而且 Redis 和 MySQL 的一致性很难保证；直接数据库行锁，量级撑得住。

5.8【P1】RabbitMQ / NATS 怎么保证消息不丢？

答：
RabbitMQ：生产者 confirm → 队列和消息持久化 → 消费者手动 ACK，业务处理完再确认；失败 Nack 重入队，超过重试次数进死信队列。QoS 设 prefetchCount=1 保证顺序。
NATS：用 JetStream 做持久化，通过统一的 queue 抽象层屏蔽底层差异（可切 Kafka）。

5.9【P0】"这个底层你懂吗？"——诚实但不减分的答法

模板：
"这个点我当时没有深入到底层实现，主要是业务驱动，用 AI 辅助生成的方案我验证过能跑通、满足需求，但源码细节没有仔细研究，这是我需要补的地方。

不过它的核心思想我了解：（说你能说的一层）。如果现在重新设计，我会先对比 A 和 B 两个方案，从 X 维度做选择。"

关键：承认 + 说清已知部分 + 展示思考路径。面试官不会因为你承认不懂而挂你，但会因为你硬撑被发现而挂你。

5.10【P2】NFT 铸造失败 / pending 太久 / Gas 谁出？

答：
铸造走异步流水线，支付成功后记录状态为"铸造中"，任一环节失败可独立重试；交易 pending 超过设定时长（【待补：当时配置的具体时间】）标记失败并触发退款；Gas 由平台代付，合约调用设置上限防止无限消耗。

5.11【P2】Docker / K8s / 可观测性（市场高频）

答：
Dockerfile 多阶段：golang 镜像编译 → alpine 运行，减小体积；Helm Chart 管理 K8s 部署，ConfigMap 管配置。
探针我理解 Liveness 失败会重启容器、Readiness 失败会从 Service 摘流量；现场排查时调过日志级别（kubectl edit deploy）、处理过 Pod Evicted 和 PVC 挂载问题。
监控接过 Prometheus 采集内存/Goroutine/HTTP 延迟，项目里也有 OpenTelemetry 的链路追踪基础；日志用 zap + lumberjack 轮转。

5.12【P2】AI 辅助开发（现在反而是加分项，要主动讲）

答：
日常用 Trae / Cursor / Claude Code 做技术调研、代码 Review 辅助和单测生成，效率提升很明显。但我会划一条线：架构设计、核心算法、安全敏感代码、资金相关逻辑坚持人工审核，AI 产出的代码必须自己能讲明白才提交。

这也是我这次面试想找的团队氛围——希望工程上既拥抱 AI，也对质量有要求。

5.13【P2】为什么选 Go？如果重来会改什么？

答：
选 Go 是因为并发模型简单、编译部署快、标准库完善，一个人开发后端时效率高；微服务用 gRPC 也方便。
如果重来：① 定时任务改成带分布式锁的调度器，避免多实例重复执行；② 敏感文件锁改成分布式方案，摆脱单机限制；③ 资金链路加独立流水对账表。
