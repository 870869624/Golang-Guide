3. 关键实现细节速查

3.1 gRPC 使用模式
· 客户端流：UploadFileSensitive(stream UploadSensitiveFileReq) returns (Response)，Recv() 到 EOF
· 服务端流：DownloadSensitiveFile(stream ...Req) returns (stream ...Resp)
· 一元 RPC：任务下发、资产查询等
· 客户端配置：Trace / Duration / Breaker / Timeout 全开，nonblock: true，mTLS 双向证书，MaxRecvMsgSize 限 10MB
· NGEDR 注入 16 个 gRPC 客户端（Agent、Asset、Rolesvc、Usersvc、Systemsvc、Syslogsvc、BFF、Logminer、Ersvc、License、Manager，以及威胁文件/软件/补丁/动态认证/移动存储等自服务）

3.2 AES-GCM 文件格式
[Nonce 12字节] [分块数 4字节 BigEndian] [密文长度1 4字节] [密文1] [密文长度2 4字节] [密文2] ...
· 密钥：文件 MD5（主）或 FileID（兼容旧版）
· Nonce 明文写文件头；每分块用块索引作 AAD，保证上下文唯一
· 下载动态解密，兼容多版本密钥回退

3.3 MongoDB 批量写入
· FileBatchWriter：缓冲通道 500，批量 50 条，10 秒强制 flush
· 两种合并策略：DefaultMergeStrategy（按 MD5 合并）/ AutoUploadMergeStrategy（按 FileID 覆盖）
· SensitiveFileUpdateQueue：全局单例，缓冲 2000 任务，单 worker 串行消费
· NGEDR：BulkWrite 无序批量（SetOrdered(false)），动态间隔聚合（1/5/15/30 分钟）

3.4 ClickHouse
· 表：sensitive_file / sensitive_file_category / sensitive_file_level / sensitive_category_level
· 聚合：groupUniqArray 做跨终端 UUID 去重，Scroll 分页替代 Offset 深分页
· 查询语义：Match / Range / Aggs
· 现场坑：Too many parts、PVC 未挂载导致 CANNOT_STATVFS

3.5 NATS 消费者 Topic
· NGDLP 7 个：aiop.ngdlp.sensitivefiletopic（5 消费者 / 100 协程池）、租户/终端/责任人删除、ERA 对账/过期/上报
· NGEDR 8 个：终端上下线、病毒事件、威胁响应日志、高级威胁事件、终端批量删除等

3.6 缓存层次
· 进程内：bigcache（大对象）→ cache2go → ttlmap（小对象 TTL）；RBAC 分组权限 LRU 缓存 5 分钟
· 分布式：Redis（会话、Token、任务队列、去重锁）；城汇玩分页缓存 TTL 1 分钟
· cwpp：进程内 bigcache / cache2go / ttlmap + 分布式 Redis

3.7 鉴权（两层体系）
· 城汇玩：JWT（golang-jwt/v4）+ 微信授权登录
· 天融信：BFF 统一 JWT 认证 / 租户隔离 / 角色注入；cwpp 用 JWT HS256+RS256 双算法 + Token 白名单 + Casbin RBAC（MongoDB adapter）
· 威胁响应：GetChildGroupIDsByRole 递归取分组 → 注入 group_id $in 实现数据隔离

3.8 城汇玩的 13 个定时任务
每 1 分钟：活动审核、通用监控、部落任务状态；每 5 分钟：账户审核、用户提现、商户提现；每日：报名统计、活动统计、部落商品结算、微信银行列表；每小时：提现状态；每 5 小时：活动结束完结分账；每月：积分结算。

3.9 支付 API 清单
JSAPI 下单（PrepayWithRequestPayment）、退款（RefundsApiService.Create）、电商分账（ProfitSharing.OrdersApiService）、完结分账（UnfreezeOrder）、回退分账（ReturnOrdersApiService）；option.WithWechatPayAutoAuthCipher 自动签名验签，PEM 私钥加载，双商户实例。

5. 技术选型对比弹药库（被问"为什么"时用）

问题    要点
ClickHouse vs MongoDB    列式存储 + 向量化执行适合 OLAP 聚合；MongoDB 适合 OLTP 和文档模型。我们分工：MongoDB 存明细、ClickHouse 做多维分析，不承载事务
RabbitMQ vs Kafka    RabbitMQ 路由灵活、可靠投递，适合支付/提现这类不能丢的中等吞吐场景；Kafka 高吞吐、日志采集场景更强
NATS vs RabbitMQ    NATS 轻量、低延迟、JetStream 补持久化；通过统一 queue 抽象层可切换
gRPC vs HTTP/JSON    HTTP/2 多路复用、头部压缩、Protobuf 高效强类型；代价是调试麻烦、浏览器支持弱
sync.Map vs map+Mutex    前者解决"动态 key 的并发安全容器"问题，`LoadOrStore` 原子；不是为了让单次加锁更快
行锁 vs Redis 扣库存    行锁在数据库内保证强一致；Redis 快但故障和双写一致性难处理，量级不大时数据库够用
本地事务 vs 分布式事务    项目规模没到需要 TCC/Saga；用本地事务 + 状态机 + 定时兜底，简单可靠
Go vs Java    并发模型简单、编译部署快、单二进制交付，适合微服务和私有化场景
