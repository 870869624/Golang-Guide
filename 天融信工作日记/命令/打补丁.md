```bash
#!/usr/bin/env bash
set -euo pipefail

usage() {
  printf '用法：bash apply_patch.sh [--arch amd|arm]\n'
  printf '默认架构为 amd；arm 使用带 -arm64-shutong 的镜像名称。\n'
}

die() {
  printf '错误：%s\n' "$*" >&2
  exit 1
}

# 在执行补丁操作前校验参数，默认使用 AMD64 镜像。
ARCH="amd"
while [[ $# -gt 0 ]]; do
  case "$1" in
    --arch)
      [[ $# -ge 2 ]] || die "--arch 缺少参数，请指定 amd 或 arm"
      ARCH="$2"
      shift 2
      ;;
    -h|--help)
      usage
      exit 0
      ;;
    *)
      die "未知参数：$1；用法：bash apply_patch.sh [--arch amd|arm]"
      ;;
  esac
done

case "$ARCH" in
  amd) IMAGE_SUFFIX="shutong" ;;
  arm) IMAGE_SUFFIX="arm64-shutong" ;;
  *) die "不支持的架构：${ARCH}，请指定 amd 或 arm" ;;
esac

# 所有补丁文件均从脚本所在目录读取，支持在任意目录执行。
SCRIPT_DIR="$(cd -- "$(dirname -- "${BASH_SOURCE[0]}")" && pwd)"
cd -- "$SCRIPT_DIR"

IMAGE_LOADER="/home/topsec/cache/gcrpi"
NAMESPACE="topsec-topaiop"
ERSVC_IMAGE="docker-hub.cloud.top/aiop/ersvc-${IMAGE_SUFFIX}:1.0.43"
NGDLP_IMAGE="docker-hub.cloud.top/ngdlp/ngdlp-${IMAGE_SUFFIX}:1.0.40"

# 按顺序加载镜像；后续补丁镜像包可继续添加到数组中。
IMAGE_PACKAGES=(
  "ersvc-shutong1009.tar"
  "ngdlp-shutong1009.tar"
)

# 执行前检查全部依赖，避免加载镜像后才发现配置文件缺失。
[[ -x "$IMAGE_LOADER" ]] || die "镜像加载工具不存在或不可执行：$IMAGE_LOADER"
[[ -x ./update_configmap.sh ]] || die "update_configmap.sh 不存在或不可执行"
command -v kubectl >/dev/null 2>&1 || die "未找到 kubectl 命令"
for file in "${IMAGE_PACKAGES[@]}" schema.json processor_resource_audited.yaml; do
  [[ -f "$file" && -r "$file" ]] || die "文件不存在或不可读取：$file"
done

for image_package in "${IMAGE_PACKAGES[@]}"; do
  printf '正在加载补丁镜像：%s\n' "$image_package"
  "$IMAGE_LOADER" -f "$image_package" || die "补丁镜像加载失败：$image_package"
done

# 仅在全部镜像加载成功后更新 ConfigMap。
printf '补丁镜像全部加载成功，正在更新 ConfigMap……\n'
./update_configmap.sh \
  --set-json-path logminer-config schema.json .default.audited_log ./schema.json \
  --set-file goms-resources processor_resource_audited.yaml ./processor_resource_audited.yaml \
  || die "ConfigMap 更新失败"

# 配置更新成功后，设置两个 Deployment 的补丁镜像。
printf '正在设置 ersvc 镜像：%s\n' "$ERSVC_IMAGE"
kubectl -n "$NAMESPACE" set image deployment/ersvc "ersvc=$ERSVC_IMAGE" \
  || die "ersvc 镜像设置失败"

printf '正在设置 ngdlp 镜像：%s\n' "$NGDLP_IMAGE"
kubectl -n "$NAMESPACE" set image deployment/ngdlp "ngdlp=$NGDLP_IMAGE" \
  || die "ngdlp 镜像设置失败；ersvc 镜像已设置，请检查部署状态"

# 设置镜像会自动触发滚动更新，等待完成后才报告成功。
for deployment in ersvc ngdlp; do
  printf '正在等待 %s 更新完成……\n' "$deployment"
  kubectl -n "$NAMESPACE" rollout status "deployment/$deployment" --timeout=300s \
    || die "$deployment 滚动更新失败或超时，请检查部署状态"
done

printf '补丁镜像加载、ConfigMap 更新及两个 Deployment 滚动更新全部完成。\n'
```

# 脚本整体说明

这是一个 **K8s 离线补丁部署脚本（bash）**，作用：离线导入镜像包 + 更新ConfigMap + 替换两个Deployment容器镜像，触发滚动升级，等待升级完成。
支持 `amd`(x86_64) / `arm`(arm64) 两种架构。

> 开头 `#!/usr/bin/env bash set -euo pipefail`
>
> - `set -e`：任意命令返回非0，脚本直接退出
> - `set -u`：使用未定义变量直接报错退出
> - `set -o pipefail`：管道中任意一段失败，整条管道返回失败码。
>   三个组合是bash严格模式，防止脚本静默出错。

```bash
IMAGE_LOADER="/home/topsec/cache/gcrpi" # 离线镜像导入工具
```

> 设计思路：**所有文件、工具先一次性校验，全部满足才开始执行；不要加载完镜像才发现yaml缺失，造成脏环境**

```bash
[[ -x "$IMAGE_LOADER" ]] || die "镜像加载工具不存在或不可执行"
[[ -x ./update_configmap.sh ]] || die "update_configmap.sh 不存在或不可执行"

  [[ -f "$file" && -r "$file" ]] || die "文件不存在或不可读取：$file"
done
```

校验清单：

1. `/home/topsec/cache/gcrpi` 存在且可执行（镜像导入工具）
2. 同目录 `update_configmap.sh` 可执行
3. 系统有kubectl命令
4. 所有镜像tar包、schema.json、processor_resource_audited.yaml 都存在并且可读

## 7. 循环加载离线镜像包

```bash
for image_package in "${IMAGE_PACKAGES[@]}"; do
  printf '正在加载补丁镜像：%s\n' "$image_package"
  "$IMAGE_LOADER" -f "$image_package" || die "补丁镜像加载失败：$image_package"
done
```

循环调用 `gcrpi` 工具导入tar镜像包到本地容器镜像。

> 离线场景：服务器无法访问外网镜像仓库，提前把镜像导出tar包，用这个工具导入。

## 8. 更新 ConfigMap

```bash
./update_configmap.sh \
--set-json-path logminer-config schema.json .default.audited_log ./schema.json \
--set-file goms-resources processor_resource_audited.yaml ./processor_resource_audited.yaml \
|| die "ConfigMap 更新失败"
```

调用同目录脚本 `update_configmap.sh`，修改k8s命名空间内的ConfigMap资源：

1. 把本地 schema.json 的内容写入ConfigMap `logminer-config` 字段
2. 把本地 processor_resource_audited.yaml 写入ConfigMap `goms-resources` 字段

> 逻辑顺序：**镜像全部导入成功之后，才修改配置**。镜像导入失败直接退出，不会污染ConfigMap。

## 9. kubectl set image 更新Deployment镜像

```bash
kubectl -n "$NAMESPACE" set image deployment/ersvc "ersvc=$ERSVC_IMAGE" || die "ersvc 镜像设置失败"
kubectl -n "$NAMESPACE" set image deployment/ngdlp "ngdlp=$NGDLP_IMAGE" || die "ngdlp 镜像设置失败；ersvc 镜像已设置，请检查部署状态"
```

`kubectl set image`：修改deployment里面容器的镜像地址。

- 修改 `ersvc` deployment 的 `ersvc` 容器镜像版本
- 修改 `ngdlp` deployment 的 `ngdlp` 容器镜像版本

> 注意错误提示：如果ersvc成功，ngdlp失败，脚本会提示 ersvc镜像已经改了，环境处于半更新状态，需要人工检查。

## 10. 等待滚动更新完成

```bash
for deployment in ersvc ngdlp; do
  printf '正在等待 %s 更新完成……\n' "$deployment"
  kubectl -n "$NAMESPACE" rollout status "deployment/$deployment" --timeout=300s \
    || die "$deployment 滚动更新失败或超时，请检查部署状态"
done
```

`kubectl rollout status`：阻塞等待Deployment滚动升级完成，最多等待300秒（5分钟）。
只有**新版本Pod就绪、旧Pod全部回收**，命令才返回成功；超时/报错直接退出。

## 11. 全部成功，打印完成提示

```bash
printf '补丁镜像加载、ConfigMap 更新及两个 Deployment 滚动更新全部完成。\n'
```

# ✅ 整体执行流程

1. 解析参数，确定amd/arm架构
2. 自动切到脚本目录
3. **一次性校验全部依赖、文件、工具**（防半更新）
4. 循环导入所有离线tar镜像包
5. 更新K8s ConfigMap配置文件
6. 修改ersvc、ngdlp两个Deployment镜像版本
7. 依次等待两个Deployment滚动升级完成，超时5分钟
8. 全部成功输出完成；任意步骤失败立刻报错退出

# ⚠️ 脚本存在的几个潜在问题（重点）

1. **IMAGE_PACKAGES 数组没有区分amd/arm**
   当你执行 `--arch arm`，镜像名称会变成 arm64-shutong，但是脚本仍然加载 `ersvc-shutong1009.tar`，不会自动加载arm版本tar包。

   > 需要手动准备arm对应的tar包，或者修改数组根据ARCH自动切换文件名。
   >
2. 滚动更新是串行等待：先等ersvc就绪，再等ngdlp。如果业务希望并行升级，可以改代码。
3. **无回滚逻辑！**
   如果升级到一半失败，脚本直接退出，**不会自动回滚镜像和ConfigMap**。需要运维手动操作kubectl回滚。
4. ConfigMap更新是直接覆盖，没有备份旧ConfigMap。建议在update_configmap.sh里增加备份，或者脚本加备份命令。
5. `set -e` 在某些复杂管道场景会失效，不过这个脚本结构简单，影响不大。
